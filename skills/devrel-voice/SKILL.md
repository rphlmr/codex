# DevRel Voice

Write for a developer with a real project who needs to understand what changes,
what can break, and what to do.

## Voice reference

Use the supplied draft, corrections, and task-specific examples first.
Otherwise read the user's approved reference:
[Relational Queries v2](https://notes.drizzle.run/articles/rqb-v2/).
Reuse it when already read in this task. If unavailable, proceed using the
available material and disclose the limitation without claiming a voice match.

Borrow how the reference explains a concrete example, what its code returns,
and likely misunderstandings. Its question headings and summary opening are
allowed. Match the requested format rather than making every post a tutorial.
The reference supplies style, not facts about another topic.

## Content and structure

- Start with the specific change or problem. Explain each fact once.
- Include implementation details only when they change what readers do,
  choose, or expect. Link deeper reference material.
- Put consequences and caveats beside the affected action. Use supported,
  concrete examples rather than invented errors or personal experience.
- For upgrades, establish the versions early and preserve package/version
  comments inside before-and-after code examples.
- Use one small running example where helpful. Explain what the code leaves
  unclear instead of narrating every line.
- Keep prerequisites, meaningful exceptions, and data-loss warnings.
- End when the useful content ends. Include a next step only when needed.

## Prose and accuracy

Speak directly to the reader with plain words and connected explanations.
Preserve useful personality and the user's phrasing. Avoid hype, staged
contrasts, fake suspense, forced punchiness, and closing recaps.
Do not use em dashes or semicolons in prose.

For a voice-only rewrite, preserve every fact, uncertainty, and strength of
claim. Add no advice, numbers, causal explanations, or invented experience.
For shortening or restructuring, consolidate repetition without dropping
information needed to act. Correct factual errors separately.

Verify examples when the environment permits. Never imply code ran or
type-checked without evidence. Keep verification gaps outside publication copy.
Before delivery, read the whole draft for repetition, factual drift, and fit
with the voice reference. Return the draft without narrating that self-check.
